## 3. Phase Commentary

> Interpretation of system behaviour at each test stage. Observed values are cited; interpretations are marked as inferred.

### Stage 1 to 5 (10 VUs to 60 VUs)

**Observed:** The system managed the increasing load well initially, maintaining a 0% error rate (source: `run/raw/summary.json → metrics.http_req_failed.values.rate`). However, latency started to build up.
**Interpretation:** As the VU count increased staircase-by-staircase up to 60 VUs, the system's request queue grew because it could not process registrations as fast as they were arriving.
**Concern / Positive note:** It's positive that no 5xx errors were thrown, meaning the server didn't crash. However, the throughput (RPS = 31.67) dropped below the baseline of 44.36 req/s, indicating a bottleneck.

### Stage 6 (90 VUs) — Abort Point

**Observed:** The test aborted approximately 11 minutes in, during the ramp-up from 60 to 90 VUs. At this point, active VUs were around 70 (source: `summary.json → metrics.vus.values.value`). The p95 latency crossed the 200 ms threshold, hitting 205.06 ms. CPU and Memory remained stable (source: `run/run-log.md`).
**Interpretation:** The `abortOnFail` safety net correctly caught the SLO violation. Because CPU and memory were not saturated, the latency spike (inferred) is almost certainly caused by SQLite's serialized write locks. When 70 concurrent users try to `POST /api/register`, they form a queue waiting for the single DB write lock.
**Concern / Positive note:** This is a classic architectural bottleneck, not a resource exhaustion issue.

## 4. Key Finding

> One paragraph. The single most important result of this test run.

The breaking point of the system is approximately 70-75 concurrent VUs, at which point the p95 latency exceeds the 200ms SLO threshold (reaching 205.06ms) due to severe request queueing, while the error rate remains flawlessly at 0%.

## 5. Performance Recommendations

> Generated by AI from measured data. Feasible / Hallucinated classification is assigned by the human reviewer at Human Gate 1. Each recommendation must cite a specific metric value and its source.

### Recommendation 1: Migrate to a Concurrent Database (PostgreSQL/MySQL)

**Basis:** `p95 latency` = 205.06 ms indicates severe request queueing despite stable CPU/Memory. Source: `run/raw/summary.json → metrics.http_req_duration.values["p(95)"]`

**Proposed action:** Since the `POST /api/register` endpoint performs writes, and SQLite serializes all writes, the application is fundamentally limited by SQLite's locking mechanism under concurrent load. Migrate the database to PostgreSQL or MySQL to support concurrent write transactions. (Note: this is an architecture-level change).

**Expected impact:** Would eliminate the database-level lock queueing, drastically reducing p95 latency under high VU loads and allowing the system to scale beyond 75 VUs.

### Recommendation 2: Offload Password Hashing

**Basis:** `Max latency` = 1109.96 ms indicates occasional extreme delays in processing. Source: `run/raw/summary.json → metrics.http_req_duration.values.max`

**Proposed action:** The `register` endpoint uses bcrypt for password hashing, which is a CPU-intensive synchronous/blocking operation. Move the bcrypt hashing logic into a Node.js Worker Thread pool so it doesn't block the main event loop.

**Expected impact:** Would prevent individual heavy hashing operations from delaying other incoming requests, reducing the `Max latency` spikes and improving overall `RPS`.

### Recommendation 3: Optimize SQLite PRAGMA Settings (If migration is not possible)

**Basis:** `RPS (avg)` = 31.67 req/s is lower than the baseline of 44.36 req/s, showing throughput degrades with concurrency. Source: `run/raw/summary.json → metrics.http_reqs.values.rate`

**Proposed action:** If migrating away from SQLite is not feasible, optimize the SQLite connection by enabling WAL (Write-Ahead Logging) mode and tuning `PRAGMA synchronous = NORMAL`.

**Expected impact:** Would increase the baseline write throughput and slightly defer the queueing bottleneck, potentially allowing the system to handle 10-20% more VUs before hitting the 200ms latency threshold.
