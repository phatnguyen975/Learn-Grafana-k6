## 1. Endpoint Analysis

### Operation Class

**Class:** Auth-Intensive

**Reasoning:** This is a registration endpoint that requires password hashing (e.g., bcrypt/argon2), making it CPU-intensive. It also involves an insertion into the database.

### Database Involvement

Performs a single INSERT operation into the `users` table. Because the SUT uses SQLite, which serialises writes, concurrent requests to this endpoint will lead to write queue saturation and potential lock contention.

### Authentication Requirement

**Requires auth:** False

This is a public endpoint. No JWT or other authentication mechanism is required to invoke it.

### Business Rules & Constraints

| Rule                 | Source (SRS section or API spec) | Impact on Testing                                                                                                                                                                     |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email uniqueness     | SRS FR-01                        | Each registration request must use a unique email address. We cannot reuse the same email in the CSV or across VU iterations, requiring robust pre-generation of dynamic emails.      |
| Password constraints | SRS FR-01                        | Passwords must be at least 8 characters and include uppercase, lowercase, number, and special character. The CSV must strictly follow this format to avoid 400 Bad Request responses. |

## 2. Test Type Justification

**Selected test type:** Stress

**Why this test type fits this endpoint:** As a write-heavy and CPU-intensive operation, registration is an excellent candidate for stress testing. Pushing the system beyond normal load will help discover the point at which the SQLite write queue saturates or CPU caps out, establishing the system's maximum concurrent registration capacity before performance degradation.

**Why other test types are less appropriate for this endpoint:** Load testing is less informative as registration is rarely a sustained steady-state operation at high volume compared to reads. Spike testing models sudden bursts, but a stress test provides a clearer curve to find the exact breaking point of the database lock mechanism.

## 5. Known Risks & Mitigations

| Risk                               | Likelihood | Mitigation                                                                                                                                            |
| ---------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email uniqueness exhaustion        | High       | Pre-generate a CSV with a large enough pool of timestamped unique emails (e.g., `perf_{timestamp}_{index}@stress.test`) to outlast the test duration. |
| SQLite database lock (SQLITE_BUSY) | High       | Stagger VU ramp-up to avoid instant lock timeouts. Document lock contention as an expected behaviour of the SUT rather than a bug.                    |
