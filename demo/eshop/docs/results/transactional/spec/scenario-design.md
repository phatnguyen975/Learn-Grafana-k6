## 1. Endpoint Analysis

### Operation Class

**Class:** Write-Simple

**Reasoning:** The `POST /api/cart` endpoint adds an item to a user's shopping cart. It involves a single database insert or update (increasing quantity if the item exists) operation per request, with no complex cascaded writes or external dependencies.

### Database Involvement

The handler for `POST /api/cart` is expected to:

1. Verify the JWT token and extract user identity.
2. Execute a `SELECT` query to check if the product already exists in the user's cart.
3. Execute an `INSERT` or `UPDATE` query to modify the cart contents.
4. Because the SUT uses SQLite, which serialises writes and does not support concurrent write transactions, concurrent `POST /api/cart` requests will experience queue-based latency spikes as requests wait for the database write lock.

### Authentication Requirement

**Requires auth:** Yes — Bearer JWT token

The API Spec (§4) states that cart endpoints require `Authorization: Bearer <token>`. The JWT is obtained via `POST /api/login`. We will use the **per-vu-cached-token** strategy, where each VU logs in once at `__ITER === 0` and caches the token for subsequent iterations.

### Business Rules & Constraints

| Rule                                  | Source (SRS section or API spec) | Impact on Testing                                                                                                                                                                                                         |
| ------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cart is user-session-specific         | FR-07 (Cart)                     | Each VU must use a unique user account (email/password). A shared account will cause data races and corrupt the cart state.                                                                                               |
| SQLite serialises writes              | AGENTS.md                        | Concurrent writes during the spike phase will inevitably queue up. High latency is expected during the spike; the test must measure the extent of this delay and ensure it doesn't result in crashes or excessive errors. |
| No account lockout on cart operations | FR-07, FR-02                     | Spike VU counts can be aggressive without triggering the login lockout (as long as login credentials are correct).                                                                                                        |

## 2. Test Type Justification

**Selected test type:** spike

**Why this test type fits this endpoint:** `POST /api/cart` is a transactional endpoint perfectly suited for simulating a flash sale or sudden promotion, where many users add products to their carts almost simultaneously. A Spike Test is designed to evaluate how the system handles sudden, extreme bursts of traffic followed by a rapid return to baseline. This helps identify if the system can process the backlog of write operations without failing or degrading permanently.

**Why other test types are less appropriate for this endpoint:**

- **Load Test:** This endpoint is a transactional write, where load is typically variable and bursty. A load test is already being executed against `read-heavy`.
- **Stress Test:** Stress testing is about finding a breaking point, but since SQLite naturally queues writes, the breaking point is an I/O artifact rather than a true app capacity limit. Stress testing is already allocated to the `auth-heavy` group.

## 5. Known Risks & Mitigations

| Risk                                 | Likelihood | Mitigation                                                                                                                                         |
| ------------------------------------ | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQLite lock contention               | High       | Expected behavior. Ensure timeouts are generous enough to not fail immediately, and focus on recovery metrics rather than just spike peak latency. |
| Account lockout                      | Low        | Ensure seed data provides 100% correct credentials for each VU to avoid the 3-fail lockout on the initial login step.                              |
| Data corruption from shared accounts | High       | Each row in the CSV must correspond to a unique user account mapped to the VU.                                                                     |
