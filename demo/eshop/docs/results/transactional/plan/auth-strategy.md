# Auth Strategy — transactional

> **Generated by:** perf-plan  
> **Date:** 2026-08-15T19:02:00+07:00  
> **Endpoint:** `POST /api/cart`  
> **Test Type:** spike

## 1. Endpoint Auth Requirement

**Requires authentication:** Yes

**Auth mechanism:** JWT Bearer token obtained via `POST /api/login`

**Session scope:** Response is specific to authenticated user (each user has their own cart).

**JWT TTL:** Unknown — assumed > test duration (1 hour default, test is 7 minutes).

## 2. Strategy Evaluation

### Strategy 1 — `setup()` Shared Token

| Dimension         | Assessment for this endpoint             |
| ----------------- | ---------------------------------------- |
| Login burden      | None                                     |
| Session realism   | Low (all VUs would modify the same cart) |
| Token expiry risk | Low                                      |
| CSV impact        | Low                                      |
| **Verdict**       | Rejected                                 |

**Rejected because:** The `POST /api/cart` endpoint requires user isolation. If all 100 VUs share the same token, they will all modify the same user's cart concurrently, leading to data conflict anomalies and unrealistic DB lock contention, failing to simulate 100 distinct users.

### Strategy 2 — Per-VU Cached Token

| Dimension         | Assessment for this endpoint             |
| ----------------- | ---------------------------------------- |
| Login burden      | High burst at start (`__ITER === 0`)     |
| Session realism   | High (each VU has isolated cart session) |
| Token expiry risk | Low (7-minute test << 1-hour TTL)        |
| CSV impact        | Needs `email` and `password` columns     |
| **Verdict**       | Selected                                 |

**Selected because:** It correctly isolates users and accurately simulates real-world behaviour where distinct users manage their own carts. The test duration is short enough that token expiry is not a concern.

### Strategy 3 — Pre-Generated Token in CSV

| Dimension         | Assessment for this endpoint                                  |
| ----------------- | ------------------------------------------------------------- |
| Login burden      | None                                                          |
| Session realism   | Moderate                                                      |
| Token expiry risk | High (tokens could expire before spike starts if not careful) |
| CSV impact        | Needs pre-generated `token` column                            |
| **Verdict**       | Rejected                                                      |

**Rejected because:** While it avoids login burden, pre-generating 100 tokens can be cumbersome and adds unnecessary token-expiry risk. Strategy 2 (Per-VU cache) is explicitly mandated in `AGENTS.md` for this specific endpoint group.

## 3. Selected Strategy

**Strategy:** Per-VU Cached Token (Strategy 2)

**Summary of reasoning:** Required for realistic user-session isolation. Instructed directly by `AGENTS.md`.

## 4. Implementation Requirements

The following constraints must be reflected in the test script built from this plan.

| Requirement            | Detail                                                          |
| ---------------------- | --------------------------------------------------------------- |
| CSV columns required   | `email`, `password`                                             |
| k6 pattern to use      | Load CSV via `SharedArray`, login once if `__ITER === 0`        |
| Login tagging          | Wrap in `group('login', () => {...})`                           |
| Login failure handling | `throw new Error(...)` if login fails to prevent cascading 401s |
