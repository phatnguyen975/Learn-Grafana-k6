## 1. Endpoint Analysis

### Operation Class

**Class:** Read-Complex

**Reasoning:** `GET /api/orders/:id` retrieves the full detail of a single order owned by the authenticated user. Based on the SRS (FR-11) and the EShop data model (a typical e-commerce order record stores header data plus a set of order-line items), the handler is expected to execute at minimum two SQL queries: one JOIN or correlated sub-query to fetch order header data and one to fetch all associated order-item rows. This is a **multi-table read** pattern, which places the endpoint firmly in the **Read-Complex** class — not Read-Simple, because a single product look-up (`GET /api/products/:id`) by contrast is a single-table fetch.

### Database Involvement

The handler for `GET /api/orders/:id` is expected to:

1. **Authenticate the request** — verify the JWT token and extract `user_id`.
2. **Fetch the order header** — `SELECT * FROM orders WHERE id = :id AND user_id = :user_id`. The `AND user_id` clause enforces FR-11 (users may only view their own orders) and also acts as the principal authorisation check.
3. **Fetch order line items** — likely a second query: `SELECT * FROM order_items WHERE order_id = :id`, potentially joined with `products` to return product names and prices.
4. **Return the assembled JSON** — no writes occur.

The SUT uses **SQLite** as its relational backend. For read operations, SQLite supports concurrent readers (WAL mode) or serialises all operations (rollback journal mode). Either way, read-only queries under low VU counts are unlikely to contend. However, at elevated concurrent VU counts (load test plateau), SQLite's page-level locking may introduce latency spikes even for reads if the database file is also being written to by other sessions concurrently. During the isolated Load Test for this endpoint, write contention is not expected because no other write-heavy test runs simultaneously.

**Potential N+1 risk:** If the ORM or query layer fetches order items in a loop per item rather than a single batch query, latency will grow linearly with the number of items per order. This must be monitored during the baseline run.

### Authentication Requirement

**Requires auth:** Yes — Bearer JWT token

`GET /api/orders/:id` requires a valid `Authorization: Bearer <token>` header (API Spec §4, FR-11). Without a valid token, the response is `401 Unauthorized` and the endpoint returns no data. Additionally, the endpoint enforces **ownership**: even a valid token for a different user will result in a `403 Forbidden` or empty response — meaning each VU must use credentials and order IDs that correspond to the same account.

**Auth flow:** The token is obtained via `POST /api/login` with valid `email` + `password`. The response body contains a `token` field (JWT string). This token is then passed as `Authorization: Bearer <token>` on every subsequent `GET /api/orders/:id` call.

**Auth strategy selected:** **Per-VU cached token** — each VU logs in exactly once at `__ITER === 0`, caches the token in a VU-local variable, and reuses it for all subsequent iterations. The login call is wrapped in a `group('login', ...)` block to exclude its latency from endpoint metrics. This strategy is correct because the API is user-session-specific (order ownership tied to `user_id`).

## 2. Test Type Justification

**Selected test type:** Load

**Why this test type fits this endpoint:** `GET /api/orders/:id` is the primary "My Orders — Detail" read path that authenticated shoppers hit repeatedly during normal shopping sessions (checking order status, tracking, verifying items). A **Load Test** is designed to verify that the system can sustain a realistic, sustained number of concurrent users at a stable throughput _without degradation_ — exactly what this endpoint needs to prove. The endpoint is read-only, produces no side-effects, and is expected to be hit multiple times per session, making it ideal for measuring steady-state performance under representative concurrent load.

**Why other test types are less appropriate for this endpoint:**

- **Stress Test:** Stress tests are designed to find the breaking point of a system by ramping VUs far beyond capacity. This is better suited to write-heavy or auth-intensive endpoints (like `POST /api/register`) where the capacity limit is tighter and more interesting to discover. For a read-only endpoint backed by SQLite in a dev environment, the stress ceiling is an artefact of SQLite's I/O model, not an actionable production bug.
- **Spike Test:** Spike tests simulate sudden, extreme traffic bursts. This pattern is more realistic for transactional endpoints (cart, checkout) where a flash-sale scenario is plausible. Sustained read access to order history is unlikely to have genuine spike traffic in an e-commerce context.
- **Soak Test:** Soak tests are appropriate for detecting memory leaks and long-term degradation. The soak test endpoint will be selected after all three primary tests are completed, based on which endpoint shows the highest p95 drift.
