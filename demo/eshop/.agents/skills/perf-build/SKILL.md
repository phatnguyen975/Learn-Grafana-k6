# perf-build — k6 Script Generation

## Overview

`perf-build` translates an approved test plan into two k6 scripts: a **sanity script** that proves the request works correctly with one VU and one iteration, and a **full test script** that implements the complete workload model with stages, thresholds, auth strategy, CSV data loading, teardown, and structured output.

The skill enforces a strict quality gate: the sanity script must pass all checks before the full script is built. The full script imports configuration values from the `tests/config/` module files rather than hardcoding them — keeping logic and configuration separate for maintainability and reuse.

### What it produces

| Artifact                                 | Purpose                                                       |
| ---------------------------------------- | ------------------------------------------------------------- |
| `build/sanity-{group}.js`                | Minimal script: 1 VU, 1 iteration, full auth, verbose logging |
| `build/sanity-result.md`                 | AI-parsed verdict for the sanity run                          |
| `build/{StudentID}_{Type}_{YYYYMMDD}.js` | Full production test script                                   |
| `build/review-notes.md`                  | Human corrections recorded after Human Gate 2                 |
| `tests/config/thresholds.js`             | Threshold values from `perf-config.json`                      |
| `tests/config/stages.js`                 | Stage definitions from the test plan                          |
| `tests/config/env.js`                    | Base URL and default headers                                  |

## When to Use

- A test plan (`test-plan.md`) and CSV data file (`{group}.csv`) have been approved.
- `perf-config.json` has non-null `workload.*`, `slo.*`, and `endpoint.auth_strategy` values.
- You need to generate the k6 script that will be executed in the test run.
- You need to verify that the endpoint, auth flow, and CSV data work correctly before committing to a full run.

## When NOT to Use

- No approved test plan exists — design the workload model first.
- The CSV data file is missing or has not been verified — generate and validate data first.
- The script already exists, is approved, and you only need to run it.
- You need to analyse test results — that is a separate concern handled after the run.

## Core Principles

1. **Sanity first, always.** The sanity script must pass all checks before any full script is written. A failing sanity means the endpoint, credentials, or CSV data has a problem that will invalidate any load result.
2. **No hardcoded configuration in scripts.** `BASE_URL`, threshold values, and stage definitions must be imported from `tests/config/` — never written as literals in the test script body.
3. **Auth flow must match the approved strategy exactly.** The strategy recorded in `perf-config.json endpoint.auth_strategy` is the single source of truth — do not deviate.
4. **Self-repair is limited.** If the sanity script fails, AI may fix and re-run a maximum of two times. After two failures, escalate to the human with a clear diagnosis — do not keep iterating silently.
5. **Teardown is not optional.** Every full script must implement `teardown()`. If no delete API exists, document this explicitly in a comment — silently omitting teardown leads to DB pollution across test runs.
6. **File naming is fixed.** The full script filename follows the exact convention: `{StudentID}_{ScenarioType}_{YYYYMMDD}.js`. Mapping: `load→LoadTest`, `stress→StressTest`, `spike→SpikeTest`, `soak→SoakTest`.

## Build Process

> Read reference files only when you reach the step that requires them.

### Step 1 — Read Inputs & Extract Context

Read `perf_config_path`. Extract and record:

- `endpoint.method`, `endpoint.path`, `endpoint.requires_auth`, `endpoint.auth_strategy`, `endpoint.payload_schema`
- `environment.base_url`
- `slo.p95_threshold_ms`, `slo.error_rate_threshold`
- `workload.normal_vus`, `workload.peak_vus`, `workload.stages`

Read `test_plan_path`. Extract and record:

- Stage table (target VU, duration, goal for each stage)
- Think time value
- `abortOnFail` condition (stress/spike only)
- Payload template (exact request body)
- Auth strategy notes and CSV column list
- Output format for this test type

Verify that `csv_data_path` exists. Read the header row and the first 3 data rows to confirm column names match what the test plan specifies. If they do not match, halt and report the discrepancy before proceeding.

Read [`references/k6-best-practices.md`](references/k6-best-practices.md) before generating any script.

### Step 2 — Generate Sanity Script

Delegate to the **`script-writer`** subagent. Provide a complete written spec:

**Sanity script requirements:**

- `options`: `{ vus: 1, iterations: 1 }` — no stages, no thresholds.
- Auth flow: implement the strategy recorded in `endpoint.auth_strategy`. See [`references/k6-best-practices.md`](references/k6-best-practices.md) for the correct k6 pattern for each strategy.
- CSV loading: use `SharedArray` to load `csv_data_path`. Read row index 0.
- Request: call the exact `method` + `path`, with the exact payload from `test_plan_path`.
- Checks: assert status code, at least one required response field, and `response time < 2000ms`.
- Logging: `console.log(JSON.stringify(response.json()))` to print the full response body.
- Output: `handleSummary(data)` writing to `{output_dir}/sanity-result.json`. Do **not** use `--summary-export`.
- No config imports in sanity script — hardcode values explicitly for readability during inspection.

Save to: `{output_dir}/sanity-{group}.js`.

Present the generated script to the human before running.

### Step 3 — Run Sanity & Self-Verify

Delegate to **`k6-runner`** subagent:

```
k6 run {output_dir}/sanity-{group}.js
```

After the run, read both stdout and `{output_dir}/sanity-result.json`. Evaluate:

| Check                    | Pass condition              | If fail                                           |
| ------------------------ | --------------------------- | ------------------------------------------------- |
| All `check()` assertions | 100% pass rate              | Fix and re-run (max 2 retries)                    |
| HTTP status code         | Expected status (e.g. 200)  | Fix auth or payload; re-run                       |
| Response body            | Required fields present     | Check API spec; fix payload; re-run               |
| Console errors           | No `ERRO` lines in stdout   | Diagnose; fix; re-run                             |
| k6 exit code             | 0 (no threshold violations) | Sanity has no thresholds — exit 99 = script error |

If all checks pass, write `{output_dir}/sanity-result.md` using [`assets/sanity-result.template.md`](assets/sanity-result.template.md) with verdict **PASS**.

If checks fail after 2 retries, write `sanity-result.md` with verdict **FAIL**, include the error diagnosis, and escalate to the human with a specific description of what failed and why.

Do **not** proceed to Step 4 until sanity verdict is **PASS**.

**[HUMAN GATE 1]** — Present `sanity-result.md` and `sanity-{group}.js`. Wait for explicit approval before building the full script. Record any requested changes.

### Step 4 — Generate Full Test Script

Read [`references/k6-best-practices.md`](references/k6-best-practices.md) and [`references/k6-anti-patterns.md`](references/k6-anti-patterns.md) before delegating.

Delegate to **`script-writer`** subagent with a complete spec:

**Full script requirements:**

- Import `{ stages }` from `tests/config/stages.js`.
- Import `{ thresholds }` from `tests/config/thresholds.js`.
- Import `{ BASE_URL, DEFAULT_HEADERS }` from `tests/config/env.js`.
- Use `SharedArray` for CSV loading.
- Auth: implement the approved strategy. Tag login requests with `group('login', () => {...})` to exclude them from endpoint metrics.
- Think time: add `sleep()` per the value in `test_plan_path`. Use randomised sleep to avoid synchronisation spikes.
- `abortOnFail`: add to threshold config for `stress` and `spike` test types per the test plan. Use `delayAbortEval: '30s'` to avoid premature abort on transient spikes.
- `teardown(data)`: implement cleanup for data created during the test. If no delete API exists, include a comment stating this explicitly.
- `handleSummary(data)`: implement the output format appropriate for `test_type`. See [`references/output-formats.md`](references/output-formats.md) for the correct format per test type.
- Filename: `{student_id}_{ScenarioType}_{YYYYMMDD}.js` where date is today's date in YYYYMMDD format and ScenarioType is mapped from `test_type`.

Save to: `{output_dir}/{student_id}_{ScenarioType}_{YYYYMMDD}.js` and `tests/{test_type}/{student_id}_{ScenarioType}_{YYYYMMDD}.js`.

**Mandatory self-review — Script Quality Checklist:** Before presenting the full script, verify every item:

- [ ] No hardcoded `BASE_URL`, threshold values, or stage arrays in the script body.
- [ ] All three `tests/config/` modules are imported and used.
- [ ] Auth strategy matches `perf-config.json endpoint.auth_strategy` exactly.
- [ ] Login requests are inside `group('login', ...)`.
- [ ] `SharedArray` is used for CSV loading, not `open()` directly in VU scope.
- [ ] `sleep()` is present with the correct value from the test plan.
- [ ] `abortOnFail` is set (stress/spike) or explicitly absent (load/soak).
- [ ] `teardown()` is implemented or its absence is justified in a comment.
- [ ] `handleSummary()` exports the correct format for the test type.
- [ ] Filename matches the exact `{StudentID}_{ScenarioType}_{YYYYMMDD}.js` convention.
- [ ] Script passes a mental dry-run: would 1 VU, 1 iteration complete without error?

Present the script with the checklist results.

**[HUMAN GATE 2]** — Human reviews the full script. Human writes corrections to `{output_dir}/review-notes.md` using [`assets/review-notes.template.md`](assets/review-notes.template.md). AI applies all corrections and presents the updated script. Human approves final version.

### Step 5 — Populate `tests/config/` Files

After the full script is approved, fill in the config module files with actual values:

**`tests/config/thresholds.js`** — use template at [`assets/thresholds.template.js`](assets/thresholds.template.js):

- `P95_THRESHOLD`: from `perf-config.json slo.p95_threshold_ms`
- `ERROR_RATE_THRESHOLD`: from `perf-config.json slo.error_rate_threshold`
- `ABORT_P95_THRESHOLD` (stress/spike): from test plan `abortOnFail` condition
- `ABORT_ERROR_RATE` (stress/spike): from test plan `abortOnFail` condition

**`tests/config/stages.js`** — use template at [`assets/stages.template.js`](assets/stages.template.js):

- Copy the stage array exactly from the approved `test_plan_path` stage table.

**`tests/config/env.js`** — use template at [`assets/env.template.js`](assets/env.template.js):

- `BASE_URL`: from `perf-config.json environment.base_url`
- `DEFAULT_HEADERS`: `{ 'Content-Type': 'application/json' }`

After writing the files, verify that the full script can resolve its imports by checking that all import paths match the file locations.

## Anti-Patterns

See [`references/k6-anti-patterns.md`](references/k6-anti-patterns.md) for a full list. Key ones:

- **Hardcoding `BASE_URL`, thresholds, or stages in the script.** Configuration belongs in `tests/config/` — hardcoded values cannot be changed without editing the script.
- **Using `open()` for CSV outside `SharedArray`.** `open()` in VU scope re-reads the file on every iteration and every VU — it does not scale and causes file descriptor exhaustion on large runs.
- **Using `--summary-export` flag.** Deprecated in k6 v0.43+, removed in v0.54+. Always use `handleSummary()`.
- **Skipping teardown because cleanup "probably won't matter".** DB pollution from one test run can cause false failures in the next (e.g. duplicate email conflicts in a registration test).
- **Proceeding to the full script when sanity fails.** A sanity failure means the fundamental request is broken. Fixing it in the full script wastes a full build cycle and may produce invalid test results.
- **Logging `response.json()` inside the VU loop in the full script.** Console logging on every iteration of a high-VU test floods stdout and degrades k6 performance. Logging belongs in the sanity script only.
- **Setting `abortOnFail` without `delayAbortEval`.** Without a delay, a single slow response triggers abort — the test stops before any meaningful data is collected.

## Best Practices

- Build the sanity script directly from the test plan's payload template — do not improvise fields or values.
- Use `Math.random() * think_range + think_min` for sleep randomisation — deterministic sleep causes all VUs to send requests simultaneously, creating artificial synchronisation spikes.
- For auth strategies that require per-VU login, always guard with `if (__ITER === 0)` to login exactly once per VU lifetime, not on every iteration.
- Add a `tags` object to the main request (`{ tags: { endpoint: '{path}', test_type: '{type}' } }`) — this makes Grafana filtering and k6 JSON output analysis much easier.
- Include a `// TEARDOWN NOTE:` comment at the top of `teardown()` explaining what data was created, what APIs are called to delete it, and what to do manually if the delete call fails.
- Keep the `tests/config/` files as the single source of truth — if threshold values need to change, update `perf-config.json` first, then regenerate the config files, not the other way around.

## Common Rationalizations to Reject

- _"The sanity fails but the issue is probably environment — I'll build the full script anyway."_ → A failing sanity means the test would produce 100% errors or invalid results. Fix the sanity first.
- _"I'll hardcode the threshold value — it's just one number."_ → Hardcoded values create drift between `perf-config.json`, `test-plan.md`, and the script. One source of truth means one place to change.
- _"Teardown is optional for this test because it's just a test environment."_ → A registration stress test can create thousands of user records. The next run will fail with duplicate email errors unless they are cleaned up. Teardown is mandatory.
- _"I'll skip the `delayAbortEval` — it keeps things simple."_ → Without the delay, a single slow response on the first iteration aborts the test before any meaningful data is collected. The delay is not optional for `abortOnFail` to work correctly.
- _"`open()` is simpler than `SharedArray` — it works fine."_ → `open()` in VU scope re-reads the CSV on every VU and every iteration. At 100+ VUs, this causes file descriptor exhaustion and degrades k6 worker performance. `SharedArray` loads once and shares across all VUs.
