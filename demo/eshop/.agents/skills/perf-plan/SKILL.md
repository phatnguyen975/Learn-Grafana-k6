# perf-plan — Workload Model, Auth Strategy & Data Design

## Overview

`perf-plan` transforms a completed baseline analysis into an actionable test plan. It reads the baseline numbers and endpoint characteristics, designs a workload model appropriate for the test type, selects an auth strategy with explicit trade-off reasoning, designs a CSV data schema, then delegates script creation and execution to generate both seed data and the final CSV file ready for use in a test script.

Every number in the workload model must be derived from the baseline measurements and hardware constraints — not assumed from generic defaults.

### What it produces

| Artifact                     | Purpose                                                      |
| ---------------------------- | ------------------------------------------------------------ |
| `plan/test-plan.md`          | Full workload model: stages, think time, thresholds, payload |
| `plan/auth-strategy.md`      | Selected auth strategy + trade-off analysis                  |
| `plan/csv-schema.md`         | Column schema, example rows, row count calculation           |
| `plan/data/seed-data.js`     | Node.js script to seed required DB records                   |
| `plan/data/generate-data.js` | Node.js script to produce the final CSV                      |
| `plan/data/{group}.csv`      | Ready-to-use CSV test data                                   |
| `perf-config.json`           | Updated with `workload.*` and `endpoint.auth_strategy`       |

## When to Use

- A baseline run has completed and `perf-config.json` has non-null `baseline.*` and `slo.*` values.
- You need to design the VU count, stage durations, think time, or thresholds for a test.
- You need to choose and justify an auth strategy for a protected endpoint.
- You need to create CSV test data or seed the database before running a test.
- You need to update `perf-config.json` with `workload.*` and `endpoint.auth_strategy`.

## When NOT to Use

- No baseline exists yet — run the baseline analysis step first.
- `perf-config.json` is missing or has null `baseline.p95_ms` — the workload model cannot be derived without measured numbers.
- The test plan and CSV already exist and are approved — proceed to script building.
- You only need to re-seed the database without changing the workload design.

## Core Principles

1. **Numbers must trace to data.** Every VU count, duration, and threshold must reference either the measured baseline or an explicit hardware constraint. Never propose round numbers without justification.
2. **Auth strategy is a reasoned decision, not a default.** All three strategies must be evaluated against the endpoint's characteristics. The chosen strategy must explain why the others were rejected.
3. **CSV rows are a resource.** Calculate the required row count from the workload model — do not use a rough guess. Underestimating rows causes test failures due to data exhaustion at runtime.
4. **Seed before generate.** The generate script reads real IDs from the API. Seed data must exist in the DB before generate-data.js runs, or the CSV will contain phantom IDs.
5. **Separate concerns.** `test-plan.md` is the workload design. `auth-strategy.md` is the auth decision. `csv-schema.md` is the data contract. Mixing them obscures the reasoning chain.
6. **Human gates are mandatory.** Workload model and CSV schema must each receive explicit human approval before any script is created or executed.

## Planning Process

> Read reference files only when you reach the step that requires them.

### Step 1 — Read Inputs & Extract Context

Read `perf_config_path` in full. Extract and note:

- `baseline.p95_ms`, `baseline.rps`, `baseline.error_rate`
- `slo.p95_threshold_ms`, `slo.error_rate_threshold`
- `endpoint.method`, `endpoint.path`, `endpoint.requires_auth`, `endpoint.payload_schema`
- `environment.host_cpu_cores`, `environment.host_ram_gb`, `environment.container_cpu_limit`, `environment.container_memory_limit`
- `workload.normal_vus` (the preliminary estimate from the baseline step, if present)

Read `scenario_design_path` and extract the VU range estimate and any noted business rule constraints.

Read `srs_path` and `api_spec_path` to confirm any rate-limit, lockout, or concurrency constraints that affect workload design. These constraints override workload model defaults.

### Step 2 — Design Workload Model & Auth Strategy

#### 2a. Workload Model

Refer to [`references/workload-patterns.md`](references/workload-patterns.md) for the canonical stage patterns, think-time guidance, and derivation formulas for each test type.

Design the model for the given `test_type`. For each value you propose, state the formula or reasoning used. The reference file provides the framework — apply it to the actual baseline numbers. Do not copy the illustrative examples from the reference as-is; derive values from `perf-config.json`.

Write `plan/test-plan.md` using [`assets/test-plan.template.md`](assets/test-plan.template.md). The document must include:

- Stages table with target VU, duration, and goal for each stage
- Think time value and the reasoning for it
- All threshold values and the formulas used to derive them
- Request payload template (exact JSON body with field descriptions)
- CSV schema summary (column names and types — full schema in Step 3)

#### 2b. Auth Strategy

Read [`references/auth-strategy.md`](references/auth-strategy.md) in full.

Analyse the target endpoint against all three strategies:

- Evaluate each strategy's suitability for this endpoint's characteristics (session scope, token lifetime risk, login load effect, CSV implications).
- Select one strategy and state clearly why the other two were rejected.
- Note any implementation requirements the chosen strategy imposes on the test script.

Write `plan/auth-strategy.md` using [`assets/auth-strategy.template.md`](assets/auth-strategy.template.md).

Update `perf-config.json`:

- Set `endpoint.auth_strategy` to the chosen strategy identifier.
- Set `workload.normal_vus`, `workload.peak_vus`, and `workload.stages` from the model.
- Update `metadata.updated_at`.

**[HUMAN GATE 1]** — Present `plan/test-plan.md` and `plan/auth-strategy.md`. Pause and wait for explicit approval of the workload model, thresholds, and auth strategy before proceeding. Record any change requests and update both documents before continuing.

### Step 3 — Design CSV Schema

Using the approved auth strategy and workload model:

1. Determine the required CSV columns based on the auth strategy (credentials, data IDs, payload fields) — see [`references/auth-strategy.md`](references/auth-strategy.md) for the CSV implications of each strategy.
2. Calculate the minimum required row count:
   - For `load`, `spike`, `soak`: `rows ≥ peak_vus` (one fixed row per VU, reused across iterations).
   - For `stress` (write-once endpoints like registration): rows must cover total unique iterations. Use the formula in [`references/row-count-formula.md`](references/row-count-formula.md) and add a 30% buffer. State the calculation explicitly.
3. Specify per-field format constraints (e.g. email uniqueness, ID must exist in DB, numeric ranges).

Write `plan/csv-schema.md` using [`assets/csv-schema.template.md`](assets/csv-schema.template.md). Include 3–5 realistic example rows (not placeholder text).

**[HUMAN GATE 2]** — Present `plan/csv-schema.md`. Wait for explicit approval before creating any scripts.

### Step 4 — Create & Run Seed Data Script

Delegate to **`script-writer`** subagent. Provide:

- The `api_spec_path` for endpoint details (login, create resource endpoints).
- The `base_url` from `perf-config.json`.
- The test type and what records need to exist (derived from the approved CSV schema).
- Output path: `plan/data/seed-data.js`.

The seed script requirements depend on `test_type` and the endpoint:

- If the CSV requires real IDs (e.g. order IDs, product IDs), the seed script must create those records via the API and print the created IDs to stdout.
- If the test type creates new records on each iteration (e.g. POST /register), no seed is needed — state this explicitly and skip script creation.
- The script must print a summary: how many records were created, and any failures.

Present `seed-data.js` content to the human before running.

Delegate execution to **`node-runner`** subagent:

```
node {output_dir}/plan/data/seed-data.js
```

Verify output: confirm the expected record count was created. If errors occur, fix the script and re-run.

### Step 5 — Create & Run Generate Data Script

Delegate to **`script-writer`** subagent. Provide:

- The approved CSV schema from `plan/data/csv-schema.md`.
- The `base_url` and any auth credentials needed to read seeded records from the API.
- The required row count from the schema document.
- Output path: `plan/data/generate-data.js` → produces `plan/data/{group}.csv`.

The generate script must:

- Read real IDs from the API (not fabricate them).
- Validate that no row contains null values.
- Validate that the row count matches the required minimum.
- For endpoints requiring unique values per iteration (e.g. unique emails): apply a deterministic generation pattern that guarantees uniqueness across runs (e.g. timestamp-prefixed or UUID-based).
- Print: output file path, total row count, and 3 sample rows.

Present `generate-data.js` content to the human before running.

Delegate execution to **`node-runner`** subagent:

```
node {output_dir}/plan/data/generate-data.js
```

After the run, verify: read the first 5 rows of `plan/data/{group}.csv`, confirm the row count, and confirm no null values in any column.

**Mandatory self-review — Test Plan Quality Checklist:** Before presenting the final output set to the human, verify every item below:

## Anti-Patterns

- **Proposing VU counts without deriving from baseline RPS.** Arbitrary round numbers (e.g. "100 VUs") without a derivation formula produce meaningless test results.
- **Selecting an auth strategy without evaluating the alternatives.** Stating "I chose Strategy 2" without explaining why Strategy 1 and Strategy 3 were rejected is not a reasoned decision.
- **Underestimating CSV row count.** For write-once endpoints (e.g. registration), running out of unique rows mid-test converts performance failures into data-conflict errors — the test becomes invalid.
- **Generating CSV with fabricated IDs.** If the CSV contains IDs that do not exist in the DB, every request fails with 404 — not a performance result.
- **Running generate-data.js before seed-data.js.** The generate script reads real IDs from the API; those IDs must exist first.
- **Mixing threshold values between test-plan.md and perf-config.json.** There must be one source of truth — `perf-config.json` — with `test-plan.md` referencing it, not re-stating different values.
- **Skipping human gate 2 because the schema looks obvious.** Schema errors discovered after script generation waste a full rebuild cycle. The gate exists to catch field name typos, missing columns, and wrong types before code is written.

## Best Practices

- Derive `normal_vus` from `baseline.rps` and a target throughput, not from a guess. Document the calculation.
- For `stress` tests, design the staircase so each step is clearly above the previous load level — a minimum of 50% increase per step is the industry convention to ensure the system is meaningfully stressed.
- For `spike` tests, the spike-to-normal ratio should be at least 3:1 to produce a meaningful measurement of recovery behaviour.
- Always set `abortOnFail: true` with a clear error rate or latency threshold for stress tests — without it, the test continues to generate load after the system has already failed, making the results hard to interpret.
- Keep the CSV schema as narrow as possible — only include columns the test script actually reads. Extra columns increase file size and add confusion.
- Use a deterministic uniqueness pattern for write-once fields (e.g. `perf_{timestamp}_{index}@test.local`) rather than random UUIDs — deterministic patterns are reproducible and easier to clean up.
- Document the cleanup procedure for seed data in `csv-schema.md`. Test data left in production-like environments can interfere with subsequent test runs.

## Common Rationalizations to Reject

- _"The VU count looks reasonable — I don't need to derive it from the baseline."_ → Reasonable-looking numbers that aren't grounded in measurement produce results that can't be compared across SUT versions.
- _"Strategy 2 is the default — I don't need to evaluate the others."_ → The auth strategy decision must be justified for this specific endpoint's session scope, token lifetime, and test type. A default that wasn't reasoned through may be wrong.
- _"I'll estimate 500 rows — that should be enough."_ → For write-once endpoints, row exhaustion mid-test is the most common cause of invalidated stress test results. Calculate the number; don't estimate it.
- _"I'll generate the CSV with fake IDs and note that they need to exist."_ → The CSV must contain real IDs. A note that IDs need to exist is not a solution — the generate script must read them from the API after seeding.
- _"The schema is simple enough to skip Human Gate 2."_ → Schema errors are the most expensive class of mistake in this workflow — they invalidate the CSV, require a script rebuild, and may corrupt seed data. The gate is mandatory.
